--------------------------------------------------------------------------------
1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Mature, security-conscious codebase. Fundamentals are right: cart pricing is
fully server-authoritative (client prices are display-only); the Stripe amount is
computed server-side and an order is marked paid ONLY by a signature-verified
webhook; RLS is enabled on all 67 tables; the admin authorization model reads
trusted DB roles (never client claims); the service-role key is server-only and
used with authorization-first discipline; strong security headers already exist;
migration 0018 shows the Supabase security linter was already run and closed
(pinned search_path, security_invoker view, revoked RPC grants).

The real risks are a small number of over-permissive RLS policies reachable
through Supabase's public PostgREST API (not the app), and the voucher/promo
layer (no atomic single-use, no owner-scoping). One latent-critical: the
multi-tenant SaaS layer added tenant plumbing but never applied per-table tenant
RLS, so onboarding a second tenant would expose all tenants' data to each other.

KEY MENTAL MODEL: the Supabase anon key is public (NEXT_PUBLIC_SUPABASE_ANON_KEY)
and PostgREST at /rest/v1 is internet-exposed. A logged-in customer holds a real
JWT and can call that API DIRECTLY, bypassing your server actions. So for
authenticated users, RLS — not your server code — is the boundary.

4. CRITICAL VULNERABILITIES
--------------------------------------------------------------------------------
[F1] No tenant isolation on any domain table  (latent CRITICAL) · P1
  Confidence High · CWE-284/639.
  Where: 0017_saas_platform.sql:5-6 (deferral stated in comment);
    0002_auth_and_rbac.sql:45-54 (staff_roles has no tenant_id); 0003:91; 0002:148.
  Evidence: 0017 added tenant_id only to `locations` and a separate tenant_users
    membership the domain RLS never consults. Every domain policy authorizes via

  Attack path: onboard tenant B -> any org-wide restaurant_manager/super_admin of

    mitigated only by a single seeded tenant + NEXT_PUBLIC_FEATURE_PLATFORM=false.
  Fix: add tenant_id to staff_roles; add current_tenant_id()-scoped predicate to
    every domain policy; gate the /platform flag. Effort: Large.

[F4] Personal loyalty/birthday vouchers not owner-scoped · P1
  High · High · CWE-639/284. src/lib/ordering/pricing.ts:171-175 looks up promo by
    ilike(code) only — no customer_id filter. Personal vouchers minted with
    customer_id (loyalty/service.ts:119-127,154-162; promo_codes.customer_id added
    0011:15). Verified: applyPromo references none of customer_id,
    per_customer_limit, first_order_only.
  Attack: any guest submits "BDAY-XXXX"/"PTS-XXXX" belonging to another customer
    -> discount applies. per_customer_limit / first_order_only (0006:13-14) are
    dead columns.
  Fix: filter applyPromo to customer_id IS NULL OR = authed uid; enforce
    per_customer_limit/first_order_only via promo_redemptions. Effort: Medium.

[F5] Promo single-use / limit not atomically enforced (unused promo_redemptions) · P1
  High · High · CWE-362/841. pricing.ts:183 checks used_count>=global_limit; the
    increment is non-atomic read-then-write far later (confirm.ts:49-52) AFTER the
    discount is baked into the Stripe charge (order/actions.ts:108-124). The table
    designed to enforce caps — promo_redemptions (0006:125-132) — is NEVER written.
  Attack: obtain a global_limit=1 code, fire N concurrent createCheckout calls ->
    all price at used_count=0, all charge discounted. "One-time" becomes unlimited.
  Fix: reserve redemption atomically at order-create via a UNIQUE-constrained
    promo_redemptions insert or a SECURITY DEFINER RPC. Effort: Medium.

[F6] globalSearch leaks cross-branch PII & live gift-card codes to any staff · P1/P2
  High · High · CWE-284/639. src/app/admin/_actions/search.ts:9-35 gated only by
    requireStaff() (rank >=1, any branch) but queries with the SERVICE client (RLS

    details, AND live gift-card codes + balances (bearer instruments).
  Fix: run through getUserClient() (RLS scopes it); never return gift-card code.
    Effort: Small.
  [IMPLEMENTED IN BATCH 1 — see Part B]

F10 INVESTIGATION — confirmed by static analysis, NOT fixed
--------------------------------------------------------------------------------
setReservationStatus (admin/_actions/reservations.ts:41-43) uses getUserClient().
A status change fires reservations_guard_status() (SECURITY INVOKER, 0005:83-104)
which INSERTs into reservation_status_history — RLS-on with NO INSERT policy
(0005:165). Under the authenticated role the insert is denied, so the whole UPDATE
errors. Guest/admin cancel via the SERVICE client is unaffected.

Could NOT run the required runtime DB test (no local Postgres). Per instruction,
NO fix applied. Reproduction encoded as the last assertion in rls_batch1_test.sql
(expects the staff update to throw today).

PROPOSED FIX (NOT APPLIED — apply only after reproducing F10 on a real DB):
  create or replace function reservations_guard_status() returns trigger
    language plpgsql security definer set search_path = public, pg_temp as $$
  declare ok boolean;
  begin
    if tg_op = 'UPDATE' and new.status is distinct from old.status then
      ok := case old.status
        when 'pending'   then new.status in ('confirmed','cancelled')
        when 'confirmed' then new.status in ('seated','cancelled','no_show')
        when 'seated'    then new.status in ('completed','cancelled')
        else false end;
      if not ok then raise exception 'illegal reservation transition % -> %', old.status, new.status; end if;
      insert into reservation_status_history (reservation_id, from_status, to_status, actor_id)
      values (new.id, old.status, new.status, auth.uid());
    end if;
    return new;
  end $$;
  revoke execute on function public.reservations_guard_status() from public, anon, authenticated;
Runs the audit insert as the function owner (bypasses the missing INSERT policy);
pinned path + revoked EXECUTE keep it tightly controlled; the insert is derived
solely from the validated transition (no user-controlled table/identifier).
